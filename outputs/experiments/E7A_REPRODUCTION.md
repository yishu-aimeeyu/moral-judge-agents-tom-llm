The first re-run did **not** agree bit-exactly: differences up to 3.1e-2, concentrated in perplexity ratios. Loosening the tolerance until that passed would have buried the question, so the difference was tracked down instead. Three measurements localise it, and each is a separate run:

Read together these say something specific. The pipeline is **deterministic**: the same script on two different A100 nodes agrees to the bit, so there is no run-to-run noise to appeal to. The original E6b job ran on an **L40S** (`outputs/logs/gpu_20124997.log`, `NVIDIA L40S`, node4204), while the first re-runs were scheduled onto **A100 80GB** nodes. Re-running on an L40S reproduces the committed numbers exactly. So the entire residual disagreement was the GPU model — fp16 kernels differ between architectures — and none of it was the construction.

## What was independently verified about the construction

- **Directions, from the lost run's own residual matrix.** `--verify-labels` rebuilds all 15 direction vectors across 3 models from the dumped `X` plus the labels: |cos| = 1.0, worst 1−|cos| = 3.3e-16.

- **Two label conventions were recovered, not guessed.** Gender's no-pronoun items fall in class 0 rather than being dropped, which is what makes the majority rate 150/298 = 0.5034; length is a median split at 21.0 words, 163/298 = 0.5470. Dropping the 10 unlabelled items instead moves the gender direction to |cos| = 0.95 and its surviving fraction from 0.9957 to 0.9850, so these were load-bearing.

- **The s ≤ 1 assertion fires live.** Each plain arm asserts the erased factor's in-sample accuracy is driven to its majority rate within 0.05 before any behavioural number is read, and `rank1_dir_eraser` refuses s > 1 outright as the E5a over-projection bug.

- **The geometry audit is still wired in.** `--verify-geometry` delegates to `66_e6_controls.py --verify`, unchanged: all consistent.

## The one thing this changes about how E6b should be read

E6b's CSVs are exactly reproducible, but **only on matched hardware**. The perplexity ratio is the most hardware-sensitive column (up to 3.1e-2 across GPU models); Δcontrast moves by at most 2e-3, which is 49× smaller than the 0.0988 effect floor E6b's conclusion rests on. No conclusion in E6_CONTROLS.md depends on the hardware, and no gate decision flips on any GPU tested.
